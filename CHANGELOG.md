# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Repository setup: agent documents (`AGENTS.md`, `docs/agents/`), coding standards, evidence standards, ship rules, pull request and issue templates, and community files.
- Plugin skeleton: `paseo-plugin.json` declaring `requirements.paseo` as `>=0.10.1 <0.11.0`, the Paseo version the smoke test targets (`0.10.1`), a strict TypeScript package, one entry module, and a test folder with a smoke test.
- One narrow host port: `server/host.ts` is the interface hook handlers use to reach Paseo, `server/paseo-host.ts` is the only module that imports the Paseo SDK, and `test/support/fake-host.ts` is the fake adapter that lets handlers be tested without a daemon.
- Harness descriptors: `harness/claude.json` holds every agent-specific fact (config directory variable, skills directory and mode, MCP delivery), `shared/harness.ts` is the field table, `server/harness.ts` loads the folder, and two checks fail when a descriptor breaks the contract or source code names an agent id.
- Resume marker: a ticket agent Paseo resumes gets its ticket marker again when its session opens (`beforeSessionOpen` on the host port, `agent.session_open` in the adapter), by its title or labels; when neither can be read it stays unmarked and one line is logged.
- Lifecycle relay: a ticket agent's turn end, pending permission, creation and archive reach its orchestrator as a message, held while the orchestrator's own turn runs, so supervision needs no heartbeat. The port gained `isRunning`; the texts live in `server/messages.ts`.
- Composer pill: each agent's composer gets a pill that counts what waits for the user (a ticket agent's open request counts toward its orchestrator, the stream agent's toward itself) and hides at zero. The port gained `onPermissionResolved` and `serveWaitingCount`; the pill's texts live in `client/pill-text.ts`. Checkpoints stay Paseo's native `AskUserQuestion`: no custom card.
- Git guard: a ticket agent's `git push`, `git checkout` and other branch-moving git are refused by a Node hook script (`guard/git-guard.mjs`, run from `hooks/hooks.json`), only where `MWP_ROLE=ticket` is set; a `beforeCreate` handler sets it for agents titled `[Wave N] <NN> ...`, so the orchestrator keeps its git. The harness descriptor gained the `guard` field (`hook` or `path-shim`), and the port hands `beforeCreate` the agent's title.
- One version token: the version lives in `package.json`, and a check fails, naming both files, when `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` differs from it, or when the contract version (`CONTRACT_VERSION` in `shared/contract.ts`, its own whole number) differs from the `Contract version:` line of `docs/contract.md`, or when `package.json` names the package differently from the Paseo id in `paseo-plugin.json`, or the marketplace entry differently from `plugin.json`. The two Claude Code manifests are new, so this repository loads as a Claude Code plugin, named `matt-with-paseo-plugin` (the Paseo id stays `matt-with-paseo`) so it can be enabled beside the skills repository's plugin, and `hooks/hooks.json` can take effect.
- Sandbox capability: the harness descriptor gained the `sandboxed` field (`true` or `false`), stated for every agent and required by the contract test; `harness/claude.json` says `true`. Nothing reads it yet, since no code routes work by harness and no screen shows one.
- Role identity: a role is read from the agent's labels (`wave` and `ticket` for a ticket agent, `stream` for the stream agent) through one helper, `shared/role-labels.ts`, which the relay and the waiting count now share, and from the env marker inside the agent; the plugin registers no provider per role, and a check fails when its code calls the SDK's provider API. A hand-started agent still needs a provider of its own.
- Situational instruction on the event: every message the plugin sends an agent ends with a `Next:` line naming the moves open to its reader, the four relay messages (by outcome for a turn end, by kind for a request) and the git guard's refusal; `combine` keeps one `Next:` line at the end of a held message. A check fails when a message type lacks the line.
- Plain words on screen: `client/pill-text.ts` holds a plain label for each term of the skills' words blocks (`PLAIN_LABELS`), and a check fails when a text the pill shows, or a literal in another client file, uses a precise term without its plain label. The precise terms stay in `server/messages.ts` and the README's development sections. The first release draws no card, so the pill is the one screen covered.
- Human words reach the orchestrator: what a person types in a ticket agent's chat is told to the orchestrator that owns it, ahead of the turn end in the same message (a `Human words:` text with the ticket, the agent and the message ids, never their text). The orchestrator's own prompts are told apart by `clientMessageId` (`server/human-words.ts`); the smoke test confirms it on a real host. The orchestrator's report listing them is the skills' part, in `hanh9898/matt-with-paseo`.
- Cheap sensor: at a ticket agent's turn end the plugin checks the conditions in `sensor/conditions.json`, one at a time, against the turn's outcome and timeline, and sends its orchestrator a `Stall suspected:` message (with a `Next:` line) only when one is flagged, so the orchestrator's stall judgement reads a transcript for that case alone. A running stream agent is checked too, between turn ends: every 5 minutes (a clock on the host port) the `quiet-running` condition flags one whose `lastActivityAt` is 30 minutes old, once per idle stretch, to its orchestrator, and so does a running ticket agent, a bundle agent included, that has a parent (the ticket and bundle agents are checked through the same tick), and every `Stall suspected:` `Next:` line now names the wave skill's hung-agent table instead of offering to prompt an agent that may be in a call. The `off-task` condition is a named slot for a small model, with none wired. No eval case yet: this repository's Claude Code plugin holds no skill an eval prompt could reach.
- Gate cap: concurrent gates are capped at a share of the machine's processors, half by default, adjusted by `MWP_GATE_SHARE` (`shared/gate-cap.ts`). When more ticket agents of one orchestrator run than the cap allows, the plugin sends the orchestrator a `Gate cap passed:` message (with a `Next:` line) telling it to queue the ready tickets; holding the spawns is the skills' part, in `hanh9898/matt-with-paseo`. The plugin stops no spawn and no shell command itself.
- Cost levels: `presets/cost-levels.json` holds the Cheap, Balanced and Max presets, each setting the agent and model of the stream, wave and ticket roles on top of Paseo's own profiles, which the plugin never creates, edits or deletes. `MWP_COST_LEVEL` picks a level and `MWP_COST_<ROLE>` (`agent/model`) overrides one role (`shared/cost-levels.ts`). Offering the levels in setup is the skills' part, in `hanh9898/matt-with-paseo`.
- State outside the repository: `shared/state-location.ts` names the per-user directory where the plugin keeps what must persist (`MWP_STATE_DIR` moves it) and the one marked block it may write in a repository's `AGENTS.md`; `server/state.ts` is the one module that writes a file, refusing names that leave the directory. Nothing persists yet: the README lists each holder of in-memory state. A check fails when any other module imports a file-writing API or a process API. The wave files stay in the integration branch's checkout, by the user's decision on #12.
- Release checklist: `docs/agents/release-checklist.md` orders the routine step for a new Paseo minor: read its changelog, run the smoke test on it, then widen `requirements.paseo` the same day with the upper bound no tighter than the evidence requires. A check fails when the item, its order after the smoke run or a pointer to the file is missing.
- CI on three systems: `.github/workflows/ci.yml` runs `npm ci`, then `npm run check`, on `ubuntu-latest`, `macos-latest` and `windows-latest`, on every pull request into `main` and every push to a `release/v*` branch; a red pull request is never merged. No pre-commit hook, Husky or Prettier is added; the pre-commit decision waits until after milestone `v0.5.0`. Running the drift check on every commit stays with `hanh9898/matt-with-paseo`, by the user's decision on #17.
- One check command: `npm run check` runs the typecheck, then every test, then the docs-set test the `test` script's glob misses, and stops at the first failure. It has no lint or format step, and the smoke steps stay manual. The README's development section and step 1 of the milestone run in the evidence standards name it.
- Release checklist and `NOTICE`: `docs/agents/release-checklist.md` lists the nine release steps in order, from cutting `release/v0.x.0` from `main` to the tag the user pushes, and keeps the host-range widening as its step 5; `NOTICE` credits sting9k/seatworks at `6d316b0` as the source of the lessons and the adapted designs, and the licence stays MIT. The README says how to install from a clone and that the plugin was tested on Node 22; `package.json` has no `engines` field. A check fails when a step, `NOTICE` or an install line is missing.
- Contract v1: `docs/contract.md` fixes what the plugin sends, reads and promises to the skills (message types with their `Next:` lines, plugin detection, labels, the ticket-agent title, checkpoint marks, answers keyed by `header`, what it reads from the `## Delegation` table, the report card shape, the required version), and ADR 0003 records where it lives and how it is versioned. `Contract version: 1` is now an integer, read by the version-token check as its own identifier, and `test/contract.test.ts` fails when the document and `server/messages.ts` disagree in either direction.
- Delegated answers: when a ticket agent or the stream agent asks an `AskUserQuestion` and the `## Delegation` table in its repository's `AGENTS.md` lets the orchestrator decide it, the plugin answers with the recommendation, keyed by header; a `Yours:` line, a `Door: one-way`, no recommendation or an unreadable table leaves it to the user (`shared/delegation.ts`, `server/delegated-answers.ts`).
- Stream agents relayed: the agent of a stream (the `stream` label and no `wave`) now has its turn end, pending permission and archive reach the orchestrator that owns it, with `stream <stream>` in place of the ticket-and-wave clause and its own `Next:` moves (`server/messages.ts`, `server/hooks/lifecycle-relay.ts`), so an unattended stream needs no heartbeat. Held messages mix stream and ticket agents in arrival order; agent created, human words, stall suspected and gate cap passed stay ticket-agent only. `docs/contract.md` gained the stream rows of the three types, and its agreement check compares them with the module.
- Appetite from turn costs: at each turn end the plugin adds an agent's `lastUsage.totalCostUsd` to its stream's total (`stream-spend.json` under the state directory), tells the orchestrator once with an `Appetite passed:` message when the total passes the `Appetite` row of the `## Delegation` table, and stops answering that stream's questions; a turn with no cost marks the total partial. The port gained `lastTurnCostUsd` (`server/appetite.ts`, `shared/appetite.ts`).
- Question budget: the plugin counts the questions it leaves to the user per day in local time, per daemon, in `question-budget.json` under the state directory, against a budget set by `MWP_QUESTION_BUDGET` (`shared/question-budget.ts`, `server/question-budget.ts`). When the budget is spent the orchestrator gets one `Question budget spent:` message (with a `Next:` line) and the composer pill says so; questions keep reaching the user and none is answered because of it. The port gained `serveBudgetSpent`; the delegated-answers reader gained `left`.
- Report card: one plugin timeline row in the orchestrator's chat, kept current under one row id, lists each delegated answer, the stream's spend against its appetite (partial when a turn had no cost) and the day's question count against the budget. It has no buttons, and a client renderer (`client/report-card.ts`, `client/report-card-view.ts`) draws it, since Paseo shows an unavailable placeholder for a plugin row with none. `docs/contract.md` and `REPORT_CARD` gained the row id and the fields of each part, and the agreement check compares them. The delegated-answers handler gained an `answered` hook and a reader of its record, and the appetite handler a `spendOf` read and an `updated` hook.
